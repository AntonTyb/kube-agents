# Design Proposal: Workload Hardening & Sandbox Default Enforcement

**Task ID:** Buganizer Task 537148050  
**Branch:** `feature/design-537148050`  
**Status:** Draft for Review  
**Findings Included:** RUNTIME-002, RUNTIME-006, RUNTIME-007

---

## Executive Summary

Autonomous AI agent workloads in Kubernetes execute untrusted, dynamic tasks driven by Large Language Models (LLMs). To adhere to the principle of defense-in-depth and prevent lateral movement or container breakout in the event of prompt injection or malicious code execution, this design proposal outlines the implementation plan for three critical workload hardening improvements:

1. **Default gVisor Kernel Isolation (RUNTIME-002):** Enable GKE Sandbox (gVisor) node pool provisioning and `runtimeClassName: gvisor` by default (`ENABLE_GVISOR=true`).
2. **Administrative Binary Stripping (RUNTIME-006):** Remove unnecessary administrative binaries (`gcloud`, `kubectl`) from the platform agent container image (`deploy/docker/Dockerfile`).
3. **Read-Only Root Filesystem Enforcement (RUNTIME-007):** Enforce `readOnlyRootFilesystem: true` across all agent container SecurityContext specifications generated by the Kubernetes operator (`k8s-operator/internal/controller/platformagent_manifests.go`).

---

## Problem Statement & Findings Analysis

### Finding RUNTIME-002: Unsandboxed Execution Runtime by Default

- **Current Behavior:** The provisioning script `k8s-operator/scripts/provision_01a_gvisor_nodepool.sh` and agent deployment script `k8s-operator/scripts/provision_07_deploy_platform_agent.sh` initialize `ENABLE_GVISOR` to `"false"`. PlatformAgent pods run on the standard host Linux kernel without gVisor user-space kernel virtualization.
- **Risk:** If a malicious prompt or compromised tool executes arbitrary syscalls, the host kernel attack surface is directly exposed.
- **Target Resolution:** Set `ENABLE_GVISOR=true` by default in provisioning scripts and default manifests.

### Finding RUNTIME-006: Administrative CLI Binaries Packaged in Container Image

- **Current Behavior:** `deploy/docker/Dockerfile` installs `google-cloud-cli`, `google-cloud-cli-gke-gcloud-auth-plugin`, and `kubectl` into the agent image via the Google Cloud apt repository.
- **Risk:** Attackers gaining execution inside the container can leverage pre-installed administrative CLIs to discover cluster resources, steal tokens, or attempt lateral movement.
- **Target Resolution:** Strip the `google-cloud-cli` and `kubectl` apt installation steps from `deploy/docker/Dockerfile`.

### Finding RUNTIME-007: Mutable Root Filesystem in Generated Pod Manifests

- **Current Behavior:** In `k8s-operator/internal/controller/platformagent_manifests.go`, the `buildBaseContainers` function defines `corev1.SecurityContext` for `platform-agent`, `platform-agent-dashboard`, and `fluent-bit` containers with `AllowPrivilegeEscalation: false` and `Drop: ALL`, but omits `ReadOnlyRootFilesystem: true`.
- **Risk:** An attacker or runaway process can write malicious binaries, modify system configurations, or tamper with installed packages on the container root filesystem.
- **Target Resolution:** Explicitly set `ReadOnlyRootFilesystem: ptr.To(true)` in the container `SecurityContext` for all generated containers.

## Technical Design & Implementation Plan

### 1. Default gVisor Sandbox Enforcement (RUNTIME-002)

#### File Modifications:

- `k8s-operator/scripts/provision_01a_gvisor_nodepool.sh`:
  Update `init_var` default value:
  ```bash
  init_var "ENABLE_GVISOR" "true" "Enable GKE Sandbox (gVisor) runtime isolation? (true/false)"
  ```
- `k8s-operator/scripts/provision_07_deploy_platform_agent.sh`:
  Update `init_var` default value:
  ```bash
  init_var "ENABLE_GVISOR" "true" "Enable GKE Sandbox (gVisor) runtime isolation? (true/false)"
  ```
- `k8s-operator/scripts/platform-agent.yaml.template`:
  Uncomment or default `runtimeClassName`:
  ```yaml
  spec:
    deployment:
      runtimeClassName: gvisor
  ```

#### Controller Behavior:

The operator controller (`k8s-operator/internal/controller/platformagent_controller.go`) already implements `validateRuntimeClass`:

- When `spec.deployment.runtimeClassName: "gvisor"` is specified, the controller verifies that the `RuntimeClass` resource exists in the cluster.
- If the node pool or RuntimeClass is not present, it transitions the Custom Resource status phase to `Degraded` with reason `RuntimeClassNotFound` or `PodUnschedulable` and outputs actionable guidance.

### 2. Stripping Administrative Binaries from Docker Image (RUNTIME-006)

#### File Modifications:

- `deploy/docker/Dockerfile`:
  Remove Section 2:
  ```dockerfile
  # REMOVE: Section 2 (google-cloud-cli and kubectl)
  - RUN curl -sSL https://packages.cloud.google.com/apt/doc/apt-key.gpg | gpg --dearmor -o /usr/share/keyrings/cloud.google.gpg && \
  -     echo "deb [signed-by=/usr/share/keyrings/cloud.google.gpg] https://packages.cloud.google.com/apt cloud-sdk main" | tee -a /etc/apt/sources.list.d/google-cloud-sdk.list && \
  -     apt-get update && apt-get install -y \
  -     google-cloud-cli \
  -     google-cloud-cli-gke-gcloud-auth-plugin \
  -     kubectl \
  -     && rm -rf /var/lib/apt/lists/*
  ```

#### Code Comment Conflict & Architectural Question:

> [!IMPORTANT]
> **Code Comment Conflict Identified:**
> In `agents/platform/scripts/platform_mcp_server.py`, lines 28–30 state:
>
> ```python
> def _run_env(extra: dict[str, str] | None = None) -> dict[str, str]:
>     """Build a subprocess env with HOME redirected to /tmp so gcloud/kubectl write credentials to the writable scratch disk inside non-root container pods."""
>     return {**os.environ, "HOME": "/tmp", **(extra or {})}
> ```
>
> Additionally, several MCP tools in `platform_mcp_server.py` (`verify_gke_cluster`, `switch_kube_context`, `list_cc_healthchecks`, `get_cc_operator_status`, `get_cc_pod_diagnostics`, `list_cc_pods`, `audit_log_searcher`) currently execute subprocess calls to `gcloud` and `kubectl`.

**Design Proposal Question / Recommendation:**

- **Conflict:** Removing `gcloud` and `kubectl` from the agent container image causes subprocess invocations in `platform_mcp_server.py` to raise `FileNotFoundError`.
- **Proposed Question for Reviewers:** Should `platform_mcp_server.py` be refactored to replace subprocess CLI calls with in-cluster Python SDKs (the official Python `kubernetes` client with in-cluster ServiceAccount token authentication, and Google Cloud client libraries such as `google-cloud-container` and `google-cloud-logging`), or should specific read-only helper micro-proxies / sidecars be used for cluster querying?
- **Recommended Approach:** Refactor `platform_mcp_server.py` to use the native Python `kubernetes` client and GCP REST/gRPC client libraries, eliminating the need for CLI binaries altogether.

### 3. Enforcing Read-Only Root Filesystem (RUNTIME-007)

#### File Modifications:

- `k8s-operator/internal/controller/platformagent_manifests.go`:
  Update `buildBaseContainers` to enforce `ReadOnlyRootFilesystem: ptr.To(true)` on all containers:

  ```go
  // 1. platform-agent container
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }

  // 2. platform-agent-dashboard container
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }

  // 3. fluent-bit container
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }
  ```

#### Writable Scratch Storage (`/tmp` emptyDir Volume Mount):

When `readOnlyRootFilesystem: true` is enforced, any runtime writes to unmounted paths (such as `/tmp` used by Python interpreters, uvicorn sockets, or scratch files) will fail with `EROFS` (Read-only file system).
To support runtime temporary operations safely:

- Add an `emptyDir` volume (e.g., `tmp-scratch`) to `buildDefaultVolumes(agent)`.
- Mount `tmp-scratch` at `/tmp` for `platform-agent` and `platform-agent-dashboard` containers.

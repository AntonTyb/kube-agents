# Design Proposal: Workload Hardening & Sandbox Default Enforcement

**Task ID:** Buganizer Task 537148050  
**Branch:** `feature/design-537148050`  
**Status:** Proposed / Ready for Review  
**Findings Included:** RUNTIME-002, RUNTIME-006, RUNTIME-007

---

## Executive Summary

Autonomous AI agent workloads in Kubernetes execute untrusted, dynamic tasks driven by Large Language Models (LLMs) and user prompts. To adhere to the principle of defense-in-depth and prevent lateral movement, privilege escalation, or container breakout in the event of prompt injection or malicious code execution, this design proposal outlines the implementation plan for three critical workload hardening improvements across the `kube-agents` repository:

1. **Default gVisor Kernel Isolation (RUNTIME-002):** Enable GKE Sandbox (gVisor) node pool provisioning and `runtimeClassName: gvisor` by default (`ENABLE_GVISOR=true`).
2. **Administrative Binary Stripping (RUNTIME-006):** Strip unnecessary administrative CLI binaries (`gcloud`, `kubectl`, `gh`) from the primary platform agent container image (`deploy/docker/Dockerfile`).
3. **Read-Only Root Filesystem Enforcement (RUNTIME-007):** Enforce `readOnlyRootFilesystem: true` across all agent container `SecurityContext` specifications generated by the Kubernetes operator (`k8s-operator/internal/controller/platformagent_manifests.go`).

> [!NOTE]
> **Historical Path Mapping:** Buganizer comments for Task 537148050 reference `k8s-operator/scripts/provision_01a_gvisor_nodepool.sh`. In the current codebase, this script has been re-numbered to `k8s-operator/scripts/provision_02_gvisor_nodepool.sh`, and the deployment script has been re-numbered from `provision_07_deploy_platform_agent.sh` to `k8s-operator/scripts/provision_08_deploy_platform_agent.sh`. All implementation references in this proposal reflect the current repository structure.

## Problem Statement & Findings Analysis

### Finding RUNTIME-002: Unsandboxed Execution Runtime by Default

- **Current Behavior:** The provisioning script `k8s-operator/scripts/provision_02_gvisor_nodepool.sh` (historically `provision_01a_gvisor_nodepool.sh`) and agent deployment script `k8s-operator/scripts/provision_08_deploy_platform_agent.sh` initialize `ENABLE_GVISOR` to `"false"`. `PlatformAgent` pods run on the standard host Linux kernel without gVisor user-space kernel virtualization by default.
- **Risk:** If a malicious prompt or compromised tool executes arbitrary syscalls or attempts a kernel vulnerability exploit, the host Linux kernel attack surface is directly exposed, risking container escape.
- **Target Resolution:** Set `ENABLE_GVISOR=true` by default in provisioning scripts and default custom resource templates.

### Finding RUNTIME-006: Administrative CLI Binaries Packaged in Container Image

- **Current Behavior:** In `deploy/docker/Dockerfile`, administrative CLI tools (`google-cloud-cli`, `kubectl`, `gh`) are installed in the `credential-proxy` container target, but historically were included directly in the agent runtime image.
- **Risk:** An attacker gaining code execution inside an agent container can leverage pre-installed administrative CLI tools to discover cluster resources, inspect service accounts, steal tokens, or attempt lateral movement across GCP and Kubernetes control planes.
- **Target Resolution:** Ensure `gcloud`, `kubectl`, `gh`, and `git` binaries are stripped from the main `agent-base` and `platform` container images, isolating credential-aware CLIs strictly to the `credential-proxy` target image.

### Finding RUNTIME-007: Mutable Root Filesystem in Generated Pod Manifests

- **Current Behavior:** In `k8s-operator/internal/controller/platformagent_manifests.go`, `buildBaseContainers` defines `corev1.SecurityContext` for `platform-agent`, `platform-agent-dashboard`, and `fluent-bit` containers with `AllowPrivilegeEscalation: ptr.To(false)` and `Capabilities: &corev1.Capabilities{Drop: []corev1.Capability{"ALL"}}`, but omits `ReadOnlyRootFilesystem: ptr.To(true)`. (Only init containers currently specify `ReadOnlyRootFilesystem: ptr.To(true)`).
- **Risk:** An attacker or runaway agent process can modify binaries, tamper with installed libraries, write executable scripts to system paths, or modify system configurations on the root filesystem.
- **Target Resolution:** Explicitly enforce `ReadOnlyRootFilesystem: ptr.To(true)` across all container `SecurityContext` definitions generated by the operator, while mounting dedicated `emptyDir` scratch volumes for `/tmp`.

## Technical Design & Implementation Plan

### 1. Default gVisor Sandbox Enforcement (RUNTIME-002)

#### File Modifications:

- `k8s-operator/scripts/provision_02_gvisor_nodepool.sh` (historically `provision_01a_gvisor_nodepool.sh`):
  Update `init_var` default value from `"false"` to `"true"`:
  ```bash
  init_var "ENABLE_GVISOR" "true" "Enable GKE Sandbox (gVisor) runtime isolation? (true/false)"
  ```
- `k8s-operator/scripts/provision_08_deploy_platform_agent.sh`:
  Update `init_var` default value from `"false"` to `"true"`:
  ```bash
  init_var "ENABLE_GVISOR" "true" "Enable GKE Sandbox (gVisor) runtime isolation? (true/false)"
  ```
- `k8s-operator/scripts/platform-agent.yaml.template`:
  Set `runtimeClassName: gvisor` by default in the template spec:
  ```yaml
  spec:
    deployment:
      runtimeClassName: gvisor
  ```

#### Controller Behavior & Validation:

The operator controller (`k8s-operator/internal/controller/platformagent_controller.go`) already implements `validateRuntimeClass`:

- When `spec.deployment.runtimeClassName: "gvisor"` is specified, the controller checks that the `RuntimeClass` resource exists in the cluster.
- If the gVisor node pool or `RuntimeClass` is missing, it transitions the Custom Resource status phase to `Degraded` with reason `RuntimeClassNotFound` or `PodUnschedulable` and outputs actionable guidance.

### 2. Stripping Administrative Binaries from Docker Image (RUNTIME-006)

#### File Modifications:

- `deploy/docker/Dockerfile`:
  Ensure Section 2 installs only credential-free utility CLIs (`yq`, `k9s`, `helm`) and python dependencies.
  Verify that the build verification step in `agent-base` actively asserts that administrative binaries are absent from the image:
  ```dockerfile
  RUN apt-get purge -y git && apt-get autoremove -y && \
      rm -rf /var/lib/apt/lists/* && \
      for binary in gcloud kubectl gh git; do \
          if command -v "${binary}" >/dev/null 2>&1; then \
              echo "unexpected credential-aware CLI in sandbox image: ${binary}" >&2; \
              exit 1; \
          fi; \
      done
  ```
  Keep the real `gcloud`, `kubectl`, and `gh` CLIs confined exclusively to the `credential-proxy` stage (`FROM platform AS credential-proxy`).

#### Code Comment Conflict & Architectural Question:

> [!IMPORTANT]
> **Code Comment Conflict Identified:**
> In `agents/platform/scripts/agent_common_server.py` (where `_run_env` was moved from `platform_mcp_server.py`), lines 48–50 state:
>
> ```python
> def _run_env(extra: dict[str, str] | None = None) -> dict[str, str]:
>     """Build a subprocess env with HOME redirected to /tmp for GKE container compatibility."""
>     return {**os.environ, "HOME": "/tmp", **(extra or {})}
> ```
>
> Historically, the original comment for `_run_env` in `platform_mcp_server.py` stated:
>
> ```python
> """Build a subprocess env with HOME redirected to /tmp so gcloud/kubectl write credentials to the writable scratch disk inside non-root container pods."""
> ```
>
> Furthermore, several MCP tools in `agents/platform/scripts/platform_mcp_server.py` (including `verify_gke_cluster`, `switch_kube_context`, `list_cc_healthchecks`, `get_cc_operator_status`, `get_cc_pod_diagnostics`, `list_cc_pods`, and `audit_log_searcher`) invoke subprocess calls to `gcloud` and `kubectl`.

**Design Proposal Question & Recommendation for Reviewers:**

- **Conflict:** Stripping `gcloud` and `kubectl` binaries from the main container image means direct subprocess calls in `platform_mcp_server.py` and other skills will fail with `FileNotFoundError` unless they rely on symlinks to a wrapper script (`credential-proxy-exec`) or a sidecar proxy.
- **Explicit Question for Reviewers:**
  _Should `platform_mcp_server.py` and other agent Python scripts be refactored to replace subprocess CLI calls (`gcloud`/`kubectl`) with native in-cluster SDKs (specifically using the Python `kubernetes` client with in-cluster ServiceAccount token authentication and official Google Cloud REST/gRPC client libraries), or should all cluster queries continue using subprocess CLI calls routed through the `credential-proxy-exec` (`credential_proxy_client.py`) symlinks?_
- **Recommended Approach:** Refactor `platform_mcp_server.py` to use official Python SDKs (`kubernetes`, `google-cloud-container`, `google-cloud-logging`). Native SDK calls eliminate shell subprocess overhead, avoid credential cache writes to `/tmp`, and enforce cleaner structured typing without depending on CLI binaries or text parsing.

### 3. Enforcing Read-Only Root Filesystem (RUNTIME-007)

#### File Modifications:

- `k8s-operator/internal/controller/platformagent_manifests.go`:
  Update `buildBaseContainers(agent)` to enforce `ReadOnlyRootFilesystem: ptr.To(true)` across all container `SecurityContext` definitions:

  ```go
  // 1. platform-agent container
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }

  // 2. platform-agent-dashboard container (if enabled)
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }

  // 3. fluent-bit container
  SecurityContext: &corev1.SecurityContext{
      ReadOnlyRootFilesystem:   ptr.To(true),
      AllowPrivilegeEscalation: ptr.To(false),
      Capabilities: &corev1.Capabilities{
          Drop: []corev1.Capability{"ALL"},
      },
  }
  ```

#### Writable Scratch Storage (`/tmp` emptyDir Volume Mount):

When `readOnlyRootFilesystem: true` is enforced, runtime writes to unmounted root filesystem paths (such as `/tmp` used by Python interpreters, FastMCP sockets, or scratch files) will fail with `EROFS` (Read-only file system).
To support runtime temporary operations safely:

- Verify and ensure an `emptyDir` volume (`tmp-scratch`) is defined in `buildDefaultVolumes(agent)`.
- Mount `tmp-scratch` at `/tmp` across `platform-agent` and `platform-agent-dashboard` containers in `buildBaseContainers(agent)`.

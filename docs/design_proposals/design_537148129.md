# Design: Inter-Agent Authentication & Session Header Security

**Task ID:** Buganizer Task 537148129  
**Status:** Proposed / Draft for Review  
**Priority:** P0 — Security & Trust Boundary Hardening  
**Target File(s):** `agents/platform/scripts/agent_common_server.py`, `agents/platform/scripts/session_manager.py`, `docs/gchat-session-metadata-data-flow.md`  
**Findings Included:** MCP-001, THREAT-003, MCP-002, MCP-004, DATA-006

---

## TL;DR

In the current multi-agent Kubernetes Agentic Harness (`kube-agents`), inter-agent communication and identity forwarding rely on shared API keys and plaintext HTTP delegation headers (`X-Hermes-*`). While previous fixes removed the insecure fallback literal `'none'` for `API_SERVER_KEY` (MCP-001), inter-agent calls remain vulnerable to identity spoofing (THREAT-003), lack cryptographic key signing and rotation mechanisms (MCP-002), omit cryptographic verification on delegation headers at downstream receivers (MCP-004), and risk telemetry/audit attribution poisoning in OpenTelemetry and `session_kv.db` (DATA-006).

This design proposal details a comprehensive, standard-library-compatible cryptographic security architecture to resolve these vulnerabilities:

1. **Strict Fail-Closed Key Management & Rotation:** Formalize primary and previous dual-key rotation (`API_SERVER_KEY` and `API_SERVER_KEY_PREVIOUS`) with zero-downtime key rotation and strict fail-closed enforcement.
2. **Cryptographic Inter-Agent Request Signing:** Introduce HMAC-SHA256 request authentication and timestamped token validation to eliminate replay attacks and protect request integrity.
3. **Cryptographically Signed Delegation Headers:** Implement canonical header serialization and HMAC-SHA256 signing for all `X-Hermes-*` delegation headers, introducing `X-Hermes-Signature` and `X-Hermes-Timestamp`.
4. **Downstream Ingress Verification & Telemetry Integrity:** Ensure downstream agents and gateways cryptographically verify delegation headers prior to populating session contexts, OpenTelemetry spans, or audit logs.

## 1. Problem Statement & Threat Model

Multi-agent coordination in `kube-agents` allows the Platform Agent and specialized subagents to delegate tasks, execute tool calls, and propagate user session contexts. However, the existing implementation exhibits five critical security vulnerabilities:

```
[ Compromised / Untrusted Agent or Network Intermediary ]
                       │
                       │ (Forged X-Hermes-User-Id / Plaintext API_SERVER_KEY)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                    agent_common_server.py                   │
│                                                             │
│  [MCP-001] Missing secret -> must fail closed (Fixed/Enforce)│
│  [MCP-002] Static API_SERVER_KEY lacks signing & rotation   │
│  [THREAT-003] Plaintext X-Hermes-* headers allow spoofing   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               │ Unverified HTTP Request
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                      session_manager.py                     │
│                                                             │
│  [MCP-004] Downstream lacks cryptographic header verify     │
│  [DATA-006] Spoofed session metadata enters session_kv.db   │
│             & poisons Hermes OTel spans                     │
└─────────────────────────────────────────────────────────────┘
```

### Finding Analysis

| Finding        | Vulnerability Description                                                                  | Impact                                                                                   | Target Remediation                                                                                         |
| :------------- | :----------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **MCP-001**    | Insecure fallback literal `'none'` for `API_SERVER_KEY` if unconfigured.                   | Unauthenticated or guessable authentication fallback.                                    | Enforce strict fail-closed validation rejecting empty/missing/whitespace keys.                             |
| **THREAT-003** | Unsigned `X-Hermes-*` delegation headers (`X-Hermes-User-Id`, `X-Hermes-Sender-Id`, etc.). | Identity spoofing across agent calls; privilege escalation to admin context.             | Cryptographically sign delegation headers using HMAC-SHA256.                                               |
| **MCP-002**    | Static shared `API_SERVER_KEY` without cryptographic signing or rotation.                  | High blast radius on key leak; inability to rotate credentials without cluster downtime. | Implement dual-key rotation (`API_SERVER_KEY` + `API_SERVER_KEY_PREVIOUS`) and time-bound request signing. |
| **MCP-004**    | Downstream receivers and gateways lack cryptographic verification for delegation headers.  | Accepting forged headers from any caller reaching the endpoint.                          | Add `verify_delegation_headers()` in `SessionManager` and reject invalid/tampered signatures.              |
| **DATA-006**   | Spoofed session headers pollute `session_kv.db` and OpenTelemetry audit spans.             | Non-repudiation failure; forensic distortion in Cloud Trace / audit logs.                | Gate session persistence and OTel attribute binding on valid cryptographic verification.                   |

## 2. Existing Architecture & Code Baseline

### Current State of Target Files

1. **`agents/platform/scripts/agent_common_server.py`**:
   - `resolve_agent_credentials(agent_id)` checks `os.environ.get("API_SERVER_KEY", "").strip()`. If empty, it raises `ValueError` (commit `308dd13`), preventing the `'none'` fallback.
   - `call_agent()` constructs an HTTP POST request to the target agent completions endpoint (`/v1/chat/completions`). It attaches `Authorization: Bearer <api_key>` and merges plaintext headers from `SESSION_MANAGER.delegation_headers(context)`.
   - Lacks request signing, timestamping, or support for key rotation.

2. **`agents/platform/scripts/session_manager.py`**:
   - `delegation_headers(context)` extracts metadata (`session_id`, `user_id`, `sender_id`, `user_email`, `chat_id`, `thread_id`) and formats standard plaintext headers (`X-Hermes-Session-Id`, `X-Hermes-User-Id`, etc.).
   - Lacks methods for generating cryptographic signatures (`X-Hermes-Signature`) or validating incoming delegation headers against active signing keys.

3. **`docs/gchat-session-metadata-data-flow.md`**:
   - Documents the session metadata flow from Google Chat Pub/Sub events -> `session_store` -> `session_kv.db` -> `session_otel_bridge` -> OpenTelemetry spans.
   - Currently documents plaintext delegation headers (`X-Hermes-*`) but does not specify cryptographic signing, verification rules, or security invariants for multi-hop agent delegation.

## 3. Proposed Technical Architecture & Design

```
┌────────────────────────────────────────────────────────────────────────┐
│                          Outgoing Request                              │
│                                                                        │
│ 1. Retrieve API_SERVER_KEY (fail-closed if missing)                    │
│ 2. Canonicalize X-Hermes-* headers                                     │
│ 3. Compute HMAC-SHA256(key, timestamp + ":" + session_id + ":" + hash) │
│ 4. Inject X-Hermes-Signature & X-Hermes-Timestamp                      │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ HTTP / REST
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                          Incoming Request                              │
│                                                                        │
│ 1. Extract X-Hermes-* headers, signature, and timestamp                │
│ 2. Validate timestamp within clock-skew window (<= 300s)               │
│ 3. Canonicalize received X-Hermes-* headers                            │
│ 4. Verify HMAC-SHA256 against API_SERVER_KEY (or PREVIOUS key)        │
│ 5. If valid: populate session context & OTel spans                     │
│    If invalid: fail closed (HTTP 401/403 or untrusted context)         │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1. Strict Fail-Closed Key Management & Rotation (MCP-001, MCP-002)

To prevent unauthenticated access and enable zero-downtime key rotation, the secret resolver is enhanced:

1. **Active Key (`API_SERVER_KEY`)**: The primary secret used for generating signatures on all outbound requests and verifying incoming requests.
2. **Previous Key (`API_SERVER_KEY_PREVIOUS`)**: An optional secondary secret accepted _only for verification_ of incoming requests during a key rotation grace window.
3. **Fail-Closed Guarantee**: If `API_SERVER_KEY` is unset, empty, or composed only of whitespace, all inter-agent operations immediately raise a `ValueError` / HTTP 500 error. No fallback literals (`"none"`, `"default"`, `""`) are permitted.

### 3.2. Canonical Header Serialization & Cryptographic Signing (THREAT-003, MCP-004)

To ensure cryptographic integrity and prevent header tampering or replay attacks:

1. **Canonical Header Representation**:
   - Collect all `X-Hermes-*` headers excluding `X-Hermes-Signature` and `X-Hermes-Timestamp`.
   - Normalize header names to lowercase and sort alphabetically by key.
   - Construct canonical string: `f"{key.lower()}:{value.strip()}\n"` for each header.
   - Compute SHA-256 digest of canonical string: `header_digest = sha256(canonical_string)`.

2. **Signature Computation**:
   - Generate current UTC timestamp in ISO 8601 or UNIX epoch seconds string.
   - Construct signing payload: `f"{timestamp}:{session_id}:{header_digest}"`.
   - Compute HMAC-SHA256 signature using `API_SERVER_KEY`:
     ```python
     signature = hmac.new(
         api_key.encode("utf-8"),
         signing_payload.encode("utf-8"),
         hashlib.sha256
     ).hexdigest()
     ```
   - Attach headers:
     - `X-Hermes-Signature`: `sha256=<hex_digest>`
     - `X-Hermes-Timestamp`: `<unix_timestamp>`

3. **Signature Verification (`verify_delegation_headers`)**:
   - Check that `X-Hermes-Signature` and `X-Hermes-Timestamp` are present.
   - Verify timestamp freshness against current system time (reject if `|now - timestamp| > max_skew_seconds`, default 300s).
   - Recompute expected HMAC-SHA256 signature against `API_SERVER_KEY`.
   - If primary match fails and `API_SERVER_KEY_PREVIOUS` is configured, test signature against `API_SERVER_KEY_PREVIOUS`.
   - Use `hmac.compare_digest` for all comparisons to prevent timing attacks.

### 3.3. Telemetry & Audit Integrity Protection (DATA-006)

- Only requests bearing valid cryptographic signatures are allowed to populate `session_kv.db` and downstream Hermes OTel span attributes (`hermes.sender.id`, `user.id`, `session.id`).
- Requests with invalid or missing signatures are flagged with `hermes.delegation.verified=false` or rejected outright, preventing audit log pollution and identity spoofing in Cloud Trace.

  - Support automatic signing when an API key is available or provided in context.

- Update the **Delegation** section to specify the signed header protocol:
  - List required headers including `X-Hermes-Signature` and `X-Hermes-Timestamp`.
  - Document the verification invariant: downstream consumers must verify the HMAC-SHA256 signature before trusting session context.
- Update **Reliability & Security Notes** to reflect cryptographic non-repudiation and replay defense.

### 4.4. `agents/platform/scripts/test_agent_common_server.py`

- Add unit tests verifying:
  1. `test_raises_when_key_unset_or_empty`: Verifies fail-closed behavior (MCP-001).
  2. `test_signed_delegation_headers`: Verifies valid HMAC-SHA256 signature generation (THREAT-003).
  3. `test_verify_delegation_headers_success`: Verifies valid header verification with `API_SERVER_KEY`.
  4. `test_verify_delegation_headers_key_rotation`: Verifies verification fallback with `API_SERVER_KEY_PREVIOUS` (MCP-002).
  5. `test_verify_delegation_headers_tampering`: Verifies tampered `X-Hermes-User-Id` is rejected (MCP-004, DATA-006).
  6. `test_verify_delegation_headers_replay_expired`: Verifies expired timestamps are rejected.

## 5. Code Comment Consistency & Explicit Design Questions

In accordance with repository guidelines, existing code comments in the codebase were analyzed to identify potential conflicts or design choices. The following explicit design questions are raised for review:

### Question 1: Standard Library (`stdlib`) Only vs External Cryptographic Libraries

- **Relevant Code Comment**: `agents/platform/scripts/test_agent_common_server.py` (lines 15-20):
  > `These tests are not wired into CI, and the credential logic under test (resolve_agent_credentials) depends only on the stdlib. When the hermes runtime deps (FastMCP / pydantic / session_manager) aren't importable, fall back to minimal stubs so the module still imports in a bare checkout.`
- **Design Resolution & Question**: To strictly honor this comment and ensure zero-dependency execution in bare checkouts, the proposed design utilizes Python standard library modules exclusively (`hmac`, `hashlib`, `time`, `base64`, `secrets`).
  - _Review Question_: Should inter-agent signing remain strictly stdlib-based (HMAC-SHA256), or is there a future requirement to introduce external JOSE/JWT dependencies (e.g. `PyJWT` or `cryptography`) in the platform container image?

### Question 2: Fail-Closed Enforcement During Key Rotation Grace Windows

- **Relevant Code Comment**: `agents/platform/scripts/agent_common_server.py` (lines 31-33) & `test_agent_common_server.py` (lines 44-45):
  > `Fail closed: never fall back to a guessable literal (e.g. "none"). A missing secret means the deployment is misconfigured; refuse to send an inter-agent request that would authenticate as a known value.`
- **Design Resolution & Question**: Outbound request signing will _always_ strictly require `API_SERVER_KEY`. Inbound verification will accept `API_SERVER_KEY` or `API_SERVER_KEY_PREVIOUS`. If neither key is configured or neither matches, the request strictly fails closed (raising `ValueError` / returning HTTP 401/500).
  - _Review Question_: Is dual-key verification (`API_SERVER_KEY` + `API_SERVER_KEY_PREVIOUS`) sufficient for all planned key rotation workflows, or should a structured JSON/Kubernetes secret key-ring format be supported?

### Question 3: Fixed Header Allowlist vs Cryptographic Control Headers

- **Relevant Code Comment**: `docs/gchat-session-metadata-data-flow.md` (lines 54-55, 85-87, 252-255):
  > `Attribution is limited to fixed fields we explicitly persist and format: session_id, Google Chat sender identity, Google Chat space/thread, and delegation headers. The code does not dynamically parse arbitrary attributes for user identity.`
- **Design Resolution & Question**: The signature headers `X-Hermes-Signature` and `X-Hermes-Timestamp` are defined as fixed control-plane headers. They are used exclusively for verification and are _not_ stored as arbitrary user identity attributes in `session_kv.db`.
  - _Review Question_: Does formally adding `X-Hermes-Signature` and `X-Hermes-Timestamp` to `SessionManager.SESSION_METADATA_KEYS` meet the design requirement for strict fixed-allowlist schemas?

### Question 4: Signature Clock Skew Window vs Long LLM Reasoning Timeouts

- **Relevant Code Comment**: `agents/platform/scripts/agent_common_server.py` (line 108):
  > `5-minute timeout to accommodate complex reasoning loops`
- **Design Resolution & Question**: The timestamp in `X-Hermes-Timestamp` is evaluated at request receipt time on incoming HTTP ingress (with a 300-second clock skew tolerance). Long-running synchronous response loops do not invalidate the ingress signature check since verification occurs upon request arrival.
  - _Review Question_: Is a 300-second (5-minute) clock-skew window optimal for multi-region GKE clusters, or should it be configurable via an environment variable (`HERMES_SIGNATURE_MAX_SKEW_SECONDS`)?

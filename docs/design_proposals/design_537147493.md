## 1. Executive Summary & Context

The `PlatformAgent` Custom Resource Definition (CRD) and its corresponding operator reconcile Kubernetes workloads that power autonomous AI agents on GKE clusters. Because AI agent workloads execute dynamic LLM-generated operations, tool invocations, and containerized utilities, securing the admission control boundary on the `PlatformAgent` CRD is critical.

This design proposal extends the Kubernetes Validating Webhook (`PlatformAgentCustomValidator`) in `k8s-operator/internal/webhook/platformagent_webhook.go` and refines CRD definitions in `k8s-operator/api/v1alpha1/common_types.go`. It establishes comprehensive validation checks to enforce security bounds on `initContainers`, `sidecars`, `env` variable overrides (specifically protecting sensitive secrets like `API_SERVER_KEY`), `volumes`, `volumeMounts`, and `RuntimeClassName`. It also addresses deletion validation, GCS lock lifecycle interactions, and resolving potential conflicts identified in existing codebase comments.

## 2. Security Findings & Technical Requirements Breakdown

| Finding ID     | Domain                  | Vulnerability / Requirement                             | Proposed Validation Enforcement                                                                                                                                                                          |
| -------------- | ----------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ADM-001**    | Admission Control       | Multi-agent conflict & webhook deadlock during deletion | Enforce single `PlatformAgent` per cluster/project limit; safely bypass validation for terminating agents (`DeletionTimestamp != nil`).                                                                  |
| **ADM-002**    | Workload Security       | Unrestricted `initContainers` & `sidecars`              | Enforce container-level security bounds on all init and sidecar containers (reject `privileged: true`, `allowPrivilegeEscalation: true`, `runAsUser: 0`, and dangerous Linux capabilities).              |
| **ADM-003**    | Env Overrides           | Overriding sensitive system environment variables       | Reject user-supplied `env` entries in `spec.deployment.env` that attempt to override critical system and security variables (e.g. `API_SERVER_KEY`, `SESSION_KV_DB_PATH`, `OTEL_*`, `TOKEN_BROKER_URL`). |
| **ADM-004**    | Storage Security        | Insecure host volumes & invalid volume mounts           | Prohibit `hostPath` volumes in `extraVolumes` and `sidecarVolumes`. Verify that all `extraVolumeMounts` reference valid declared volumes and do not overwrite protected system mount paths.              |
| **ARCH-003**   | Architecture / Sandbox  | Insecure or unvalidated container runtime classes       | Validate `spec.deployment.runtimeClassName` format and ensure it aligns with approved container isolation runtimes (e.g. `gvisor`).                                                                      |
| **THREAT-004** | Threat Modeling         | Container breakout & privilege escalation               | Ensure comprehensive defense-in-depth across pod and container security contexts, blocking privilege escalation vectors.                                                                                 |
| **PI-003**     | Prompt Injection / Auth | Plaintext API key injection & credential tampering      | Ensure `API_SERVER_KEY` is exclusively populated via `ApiServerSecretRef` (SecretKeySelector) and cannot be injected via plaintext `spec.deployment.env`.                                                |

## 3. Detailed Technical Design & Implementation Plan

### 3.1. Webhook Validation Architecture

The validating webhook operates via `PlatformAgentCustomValidator`, implementing `admission.CustomValidator`. The validation flow is structured into modular validation helpers invoked during `ValidateCreate` and `ValidateUpdate`:

```
                    [ Admission Request (Create / Update / Delete) ]
                                          │
                                          ▼
                         ┌─────────────────────────────────┐
                         │   Is DeletionTimestamp != nil?  │
                         └─────────────────────────────────┘
                                  │               │
                             YES  │               │ NO
                                  ▼               ▼
                       [ Return (nil, nil) ]   [ validatePlatformAgent() ]
                                                  │
                ┌─────────────────────────────────┼─────────────────────────────────┐
                ▼                                 ▼                                 ▼
      [ 1. Singleton Check ]           [ 2. RuntimeClass Check ]         [ 3. Env Overrides Check ]
       (ADM-001: 1 per cluster)          (ARCH-003: gvisor/valid)         (ADM-003, PI-003: API_SERVER_KEY)
                │                                 │                                 │
                └─────────────────────────────────┼─────────────────────────────────┘
                                                  │
                ┌─────────────────────────────────┴─────────────────────────────────┐
                ▼                                                                   ▼
      [ 4. Container Security Check ]                                     [ 5. Volume Security Check ]
       (ADM-002, THREAT-004: init/sidecars)                                (ADM-004: block hostPath, verify mounts)
```

### 3.2. Detailed Validation Logic by Component

#### 3.2.1. Environment Variable Overrides Validation (ADM-003, PI-003)

In `k8s-operator/internal/webhook/platformagent_webhook.go`, validate `spec.deployment.env`:

- Define a protected set of reserved environment variable names:
  ```go
  var protectedEnvVars = map[string]struct{}{
      "API_SERVER_KEY":              {},
      "SESSION_KV_DB_PATH":         {},
      "PLATFORM_AGENT_HOME":        {},
      "HOME":                       {},
      "API_SERVER_ENABLED":         {},
      "API_SERVER_HOST":            {},
      "OTEL_SERVICE_NAME":          {},
      "OTEL_EXPORTER_OTLP_ENDPOINT": {},
      "OTEL_EXPORTER_OTLP_PROTOCOL": {},
      "OTEL_RESOURCE_ATTRIBUTES":    {},
      "TOKEN_BROKER_URL":           {},
      "GOOGLE_CHAT_PROJECT_ID":     {},
      "GOOGLE_CHAT_SUBSCRIPTION_NAME": {},
      "GOOGLE_CHAT_ALLOWED_USERS":  {},
      "GOOGLE_CHAT_HOME_CHANNEL":   {},
      "GOOGLE_CHAT_ALLOW_ALL_USERS": {},
      "SLACK_BOT_TOKEN":            {},
      "SLACK_APP_TOKEN":            {},
      "SLACK_ALLOWED_USERS":        {},
      "SLACK_ALLOW_ALL_USERS":      {},
      "SLACK_HOME_CHANNEL":         {},
      "SLACK_HOME_CHANNEL_NAME":    {},
  }
  ```
- Validation Function `validateEnvOverrides(fldPath *field.Path, envVars []corev1.EnvVar) field.ErrorList`:
  - Iterate over `envVars`. For any entry whose `Name` belongs to `protectedEnvVars`, append `field.Forbidden(fldPath.Index(i).Child("name"), fmt.Sprintf("environment variable %q is managed by the operator and cannot be overridden in deployment.env", env.Name))`.
  - Specifically prevents plaintext `API_SERVER_KEY` injection (PI-003), ensuring credentials are only passed via `spec.harness.hermes.apiServerSecretRef`.

#### 3.2.2. Container Security Bounds Validation (ADM-002, THREAT-004)

Validate both `spec.deployment.initContainers` and `spec.deployment.sidecars`:

- Validation Function `validateContainerSecurity(fldPath *field.Path, containers []corev1.Container) field.ErrorList`:
  - For each container:
    1. **Privileged Mode**: If `c.SecurityContext != nil && c.SecurityContext.Privileged != nil && *c.SecurityContext.Privileged`, return `field.Forbidden(fldPath.Index(i).Child("securityContext", "privileged"), "privileged mode is forbidden")`.
    2. **Privilege Escalation**: If `c.SecurityContext != nil && c.SecurityContext.AllowPrivilegeEscalation != nil && *c.SecurityContext.AllowPrivilegeEscalation`, return `field.Forbidden(fldPath.Index(i).Child("securityContext", "allowPrivilegeEscalation"), "allowPrivilegeEscalation must not be true")`.
    3. **Root User / Group**: If `c.SecurityContext != nil && c.SecurityContext.RunAsUser != nil && *c.SecurityContext.RunAsUser == 0`, return `field.Forbidden(fldPath.Index(i).Child("securityContext", "runAsUser"), "running as root (UID 0) is forbidden")`. Similarly reject `RunAsGroup == 0`.
    4. **Dangerous Capabilities**: If `c.SecurityContext != nil && c.SecurityContext.Capabilities != nil`, inspect `Capabilities.Add`. Reject dangerous capabilities:
       `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_NET_RAW`, `CAP_SYS_MODULE`, `CAP_SYS_PTRACE`, `CAP_DAC_OVERRIDE`, `CAP_SYS_CHROOT`.
    5. **Image Requirement**: Ensure `c.Image != ""` (reject empty image strings).

#### 3.2.3. Volumes and Volume Mounts Validation (ADM-004)

Validate `spec.deployment.extraVolumes`, `spec.deployment.sidecarVolumes`, and `spec.deployment.extraVolumeMounts`:

- Validation Function `validateVolumesAndMounts(fldPath *field.Path, dep *agentv1alpha1.DeploymentSpec) field.ErrorList`:
  1. **Forbidden Volume Types (`hostPath`)**:
     - Iterate through `extraVolumes` and `sidecarVolumes`.
     - If `vol.HostPath != nil`, return `field.Forbidden(fldPath.Child("extraVolumes").Index(i).Child("hostPath"), "hostPath volumes are forbidden for security isolation")`.
  2. **Volume Reference Integrity**:
     - Construct a map of all valid volume names: default volumes (`platform-agent-data-vol`, `platform-agent-config-vol`, `settings-volume`, `system-metadata`, `fluent-bit-config`, `fluent-bit-state`) plus names from `extraVolumes` and `sidecarVolumes`.
     - Iterate through `dep.ExtraVolumeMounts`. If `mount.Name` does not exist in the map of valid volume names, return `field.NotFound(fldPath.Child("extraVolumeMounts").Index(i).Child("name"), mount.Name)`.
  3. **Protected Mount Paths**:
     - Prohibit `extraVolumeMounts` from mounting over sensitive system paths (e.g. `/var/lib/kube-agents/session` or `/fluent-bit/etc`).

#### 3.2.4. RuntimeClass Validation (ARCH-003)

Validate `spec.deployment.runtimeClassName`:

- Validation Function `validateRuntimeClassName(fldPath *field.Path, rcName *string) field.ErrorList`:
  - If `rcName != nil && *rcName != ""`:
    - Verify string adheres to Kubernetes RFC 1123 subdomain naming rules.
    - Emit admission warning if `rcName` is set to an unverified runtime class or if `BrowserArgs` contains `--no-sandbox` without a sandboxed runtime class such as `gvisor`.

#### 3.2.5. Deletion Validation & GCS Lock Release (`ValidateDelete`)

- Currently `ValidateDelete` in `platformagent_webhook.go` is a stub.
- Implementation for `ValidateDelete`:
  ```go
  func (v *PlatformAgentCustomValidator) ValidateDelete(ctx context.Context, obj runtime.Object) (admission.Warnings, error) {
      platformAgent, ok := obj.(*agentv1alpha1.PlatformAgent)
      if !ok {
          return nil, fmt.Errorf("expected a PlatformAgent object but got %T", obj)
      }
      platformagentlog.Info("validating PlatformAgent deletion", "name", platformAgent.Name, "namespace", platformAgent.Namespace)

      // Ensure deletion is allowed and log audit metadata for finalizer/lock teardown
      return nil, nil
  }
  ```
- Controller teardown in `platformagent_controller.go` (`handleDeletion`) manages releasing cluster resources, deleting RBAC bindings (`kubeagents:viewer:*`, `kubeagents:explorer:*`), and stripping the finalizer (`kubeagents.x-k8s.io/finalizer` and `kubeagents.x-k8s.io/platformagent-webhook-lock`).

## 4. Code Comment Analysis & Explicit Design Questions

In accordance with requirement #3, we have analyzed all relevant code comments in the target codebase. Below are explicit design questions and conflict evaluations raised by comments in the code:

### Question 1: Terminating Agent Validation Exemption vs. Spec Mutation Protection

- **Relevant Code Comments:**
  - `platformagent_webhook.go:103`: `// Skip validation for terminating agents to avoid deadlocks during deletion (e.g. finalizer removal)`
  - `platformagent_webhook.go:115`: `// Skip terminating agents to prevent deadlocking new platformagent deployment`
- **Design Evaluation & Question:**
  - _Question:_ Does skipping validation unconditionally when `platformAgent.DeletionTimestamp != nil` create a loophole where an update could inject invalid specs during resource termination?
  - _Proposed Resolution:_ The admission skip for `DeletionTimestamp != nil` is necessary in Kubernetes because controller finalizer removal is executed via `client.Update()`, which triggers `ValidateUpdate`. If `ValidateUpdate` evaluated the full spec on terminating objects, any legacy or invalid fields would block finalizer removal and cause a deadlock. Therefore, the design maintains the immediate return `if platformAgent.DeletionTimestamp != nil { return nil, nil }` at the top of `validatePlatformAgent`. For update requests on terminating agents where `spec` is modified, we raise the question of whether to reject `spec` changes while permitting `metadata.finalizers` changes.

### Question 2: Decoupled Deployment Model vs. Strict Webhook Security Constraints

- **Relevant Code Comments:**
  - `common_types.go:87-88`: `// DeploymentSpec abstracts the Kubernetes Pod/Deployment configuration, completely decoupling the compute payload from the agent's application logic.`
- **Design Evaluation & Question:**
  - _Question:_ Does enforcing validating webhook constraints on `initContainers`, `sidecars`, `extraVolumes`, and `env` contradict the design goal of "completely decoupling the compute payload"?
  - _Proposed Resolution:_ Decoupling compute configuration does not imply permitting insecure configurations. The validating webhook acts as an admission firewall that enforces organizational and cluster security bounds (least privilege, non-root execution, secret isolation) without coupling the CRD to specific container binaries or application payloads.

### Question 3: `ValidateDelete` Validation Scope vs. Asynchronous Controller Lock Release

- **Relevant Code Comments:**
  - `platformagent_controller.go:172`: `// Resource is deleted. Safe to remove finalizer and update.`
  - `platformagent_webhook.go:140`: `// TODO(user): fill in validation logic here`
  - `platformagent_webhook_test.go:71`: `Finalizers: []string{"kubeagents.x-k8s.io/platformagent-webhook-lock"}`
- **Design Evaluation & Question:**
  - _Question:_ Should `ValidateDelete` attempt synchronous verification of external state/storage locks (e.g., GCS bucket locks), or should lock release remain exclusively in the controller reconciler?
  - _Proposed Resolution:_ `ValidateDelete` must execute quickly and fail-safe. Performing external network RPCs (such as checking GCS locks) inside an admission webhook path introduces webhook timeouts and API server degradation. Therefore, `ValidateDelete` validates the admission request metadata, while the controller reconciler (`handleDeletion`) executes finalizer teardown and external lock releases.

### Question 4: Browser `--no-sandbox` Flag vs. Sandboxed RuntimeClass Requirement

- **Relevant Code Comments:**
  - `common_types.go:105`: `// BrowserArgs specifies custom command-line arguments to pass to the agent's browser (e.g. --no-sandbox).`
- **Design Evaluation & Question:**
  - _Question:_ Should the validating webhook reject `--no-sandbox` in `BrowserArgs` if `RuntimeClassName` is not set to a secure sandbox (e.g. `gvisor`)?
  - _Proposed Resolution:_ Headless browser automation in unprivileged containers frequently requires `--no-sandbox`. The validating webhook will return an admission warning (`admission.Warnings`) when `--no-sandbox` is specified without `RuntimeClassName: gvisor`, advising administrators to enable GKE Sandbox for browser automation workloads.

## 5. Verification Plan & Test Strategy

### 5.1. Unit Test Coverage (`platformagent_webhook_test.go`)

Extend `TestPlatformAgentValidation` in `k8s-operator/internal/webhook/platformagent_webhook_test.go` with test cases covering all findings:

1. **ADM-001**: Single-instance project limit validation (create duplicate -> rejected; update existing -> allowed; terminating existing -> allowed).
2. **ADM-002 & THREAT-004**:
   - `initContainer` with `privileged: true` -> rejected.
   - `sidecar` with `allowPrivilegeEscalation: true` -> rejected.
   - `initContainer` with `runAsUser: 0` -> rejected.
   - `sidecar` adding `CAP_SYS_ADMIN` -> rejected.
3. **ADM-003 & PI-003**:
   - Custom `env` containing `API_SERVER_KEY` -> rejected with field forbidden error.
   - Custom `env` containing `SESSION_KV_DB_PATH` or `OTEL_EXPORTER_OTLP_ENDPOINT` -> rejected.
   - Legitimate custom env (e.g., `CUSTOM_VAR`) -> allowed.
4. **ADM-004**:
   - `extraVolumes` containing `hostPath` -> rejected.
   - `extraVolumeMounts` referencing non-existent volume name -> rejected.
5. **ARCH-003**:
   - Valid `runtimeClassName: "gvisor"` -> allowed.
   - Invalid format for `runtimeClassName` -> rejected.
6. **ValidateDelete**:
   - `ValidateDelete` returns `nil, nil` for valid agent deletion.

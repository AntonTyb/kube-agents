# Design Proposal: Buganizer Task 537148738 — CI/CD Pipeline Security Scanning & Dependency Management

**Task Reference:** Buganizer Task 537148738  
**Author:** Platform Engineering & Security Team  
**Status:** Draft / Under Review  
**Target Files:** `.github/workflows/*`, `.github/dependabot.yml`  
**Findings Included:** PIPE-001, PIPE-002, PIPE-003, PIPE-005, PIPE-006

---

## 1. Executive Summary

This technical design proposal establishes a comprehensive security hardening and automated governance framework for the `kube-agents` CI/CD infrastructure on GitHub Actions. By addressing findings PIPE-001 through PIPE-006, this design implements immutable action SHA pinning, safe output variable encapsulation, multi-layered static security analysis (`gosec`, `trivy`, `semgrep`, `checkov`), full-stack Dependabot ecosystem coverage (Go, Python, Node.js, Docker, Actions), and strict least-privilege workflow permissions.

---

## 2. Security Findings & Detailed Assessment

### 2.1 PIPE-001: Unpinned Third-Party GitHub Actions

- **Current State:** Workflows throughout `.github/workflows/` reference third-party GitHub Actions via floating branch or tag identifiers (e.g., `uses: actions/checkout@v7`, `uses: docker/build-push-action@v7`, `uses: actions/setup-go@v7`).
- **Security Risk:** Mutable tag references can be updated or overwritten upstream (either intentionally or via account compromise), introducing supply chain attack vectors or unexpected breaking changes into build pipelines.
- **Target Fix:** Pin every action invocation to an immutable 40-character git commit SHA, accompanied by an inline comment indicating the release tag (e.g., `uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`). Container images used in workflow jobs must similarly be pinned to explicit version tags and immutable SHA256 digests (e.g., `image: semgrep/semgrep:1.82.0@sha256:...`) rather than defaulting to mutable floating tags or `latest`.

### 2.2 PIPE-002: Insecure `$GITHUB_OUTPUT` Writes & Unverified Binary Downloads

- **Current State:**
  - In `docker-publish-gcp.yml` and `reusable-deploy-integrations.yml`, dynamic step outputs are written directly using single-line string concatenation (`echo "digest=$DIGEST" >> "$GITHUB_OUTPUT"`).
  - In `actionlint.yml`, binary dependencies are retrieved via unverified `curl -sSfL` downloads without hash verification.
- **Security Risk:**
  - Direct string concatenation without heredoc delimiters can lead to output truncation, multiline line-injection, or broken workflow evaluation if output strings contain spaces, newlines, or control characters.
  - Downloading unverified binaries via `curl` introduces remote code execution and supply chain risks.
- **Target Fix:** Standardize output writes to use safe heredoc delimiter syntax (`{ echo "key<<EOF"; echo "$VAL"; echo "EOF"; } >> "$GITHUB_OUTPUT"`) and replace raw `curl` scripts with official, pinned GitHub Actions (`rhysd/actionlint-action`).

### 2.3 PIPE-003: Missing Static Security Analysis Scanners

- **Current State:** CI pipelines lack automated static security scanners for Go source code, container images, Infrastructure-as-Code (Kubernetes manifests, Helm charts, Dockerfiles), and Python scripts.
- **Security Risk:** Vulnerabilities such as hardcoded credentials, permissive Kubernetes RBAC/Pod security policies, outdated container bases, or unsafe code patterns can bypass review into production.
- **Target Fix:** Implement a dedicated, multi-job `.github/workflows/security-scan.yml` incorporating `gosec` (Go SAST), `trivy` (container & manifest misconfiguration scan), `semgrep` (multi-language SAST), and `checkov` (IaC compliance).

### 2.4 PIPE-005: Incomplete Dependabot Ecosystem Coverage

- **Current State:** `.github/dependabot.yml` monitors only `github-actions` at the root and `docker` for subdirectories `/agents/platform`, `/agents/operator`, `/agents/devteam`. It lacks tracking for Go (`k8s-operator/go.mod`), Python (`tests/e2e/requirements.txt`), Node.js (`docs/site/package.json`), and additional Docker directories (`deploy/docker`).
- **Security Risk:** Outdated language packages and dependencies are left unmonitored for known CVEs.
- **Target Fix:** Expand `.github/dependabot.yml` to include `gomod`, `pip`, `npm`, and additional `docker` directory updates on a scheduled weekly cadence.

### 2.5 PIPE-006: Insecure Event Triggers & Permissive Permissions Hygiene

- **Current State:** Certain workflows lack top-level `permissions:` blocks or require review for dangerous triggers (e.g. `pull_request_target`).
- **Security Risk:** Workflows executed without strict permission boundaries can be exploited to modify repository state or leak credentials.
- **Target Fix:** Enforce top-level `permissions: contents: read` across all workflow files, restricting elevated permissions (`id-token: write`, `pull-requests: write`) exclusively to necessary jobs.

### 3.2 Output Sanitization & Safe Scripting (PIPE-002)

1. Update `docker-publish-gcp.yml` output writes:

   ```bash
   # Before:
   # echo "digest=$DIGEST" >> "$GITHUB_OUTPUT"

   # After:
   {
     echo "digest<<EOF"
     echo "$DIGEST"
     echo "EOF"
   } >> "$GITHUB_OUTPUT"
   ```

2. Replace actionlint script downloading in `.github/workflows/actionlint.yml`:
   ```yaml
   name: Actionlint

   on:
     push:
       branches: [main]
     pull_request:
       branches: [main]

   permissions:
     contents: read

   jobs:
     actionlint:
       runs-on: ubuntu-latest
       steps:
         - name: Checkout code
           uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1

         - name: Run actionlint
           uses: rhysd/actionlint-action@486e9cd4ae9876778f654b9d08e5033734eb60e1 # v1.7.7
   ```

### 3.3 Automated Security Scanning Workflow (PIPE-003)

Create `.github/workflows/security-scan.yml` with four dedicated jobs:

```yaml
name: Security Scanning

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 4 * * 1" # Weekly Monday scan

permissions:
  contents: read

jobs:
  gosec-scan:
    name: Go Security Scan (gosec)
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Run gosec
        uses: securego/gosec@e0cca6fe95306b7e7790d6f1bf6a7bec6d622459 # v2.22.0
        with:
          args: "./k8s-operator/..."

  trivy-scan:
    name: Container & Manifest Scan (trivy)
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Scan Repository Configs & Manifests
        uses: aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25 # v0.36.0
        with:
          scan-type: "config"
          exit-code: "1"
          severity: "HIGH,CRITICAL"
          trivyignores: ".trivyignore.yaml"

  semgrep-scan:
    name: SAST Scan (semgrep)
    runs-on: ubuntu-latest
    container:
      image: semgrep/semgrep:1.155.0@sha256:cc869c685dcc0fe497c86258da9f205397d8108e56d21a86082ea4886e52784d
    steps:
      - name: Checkout code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Run semgrep
        run: semgrep ci --config=p/security-audit

  checkov-scan:
    name: IaC Security Scan (checkov)
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Run Checkov
        uses: bridgecrewio/checkov-action@69437f47399a9e321cd0f08938cb5cf2bb846dba # v12.2928.0
        with:
          framework: all
          output_format: cli
          soft_fail: true
```

### 3.5 Permissions Scoping & Event Trigger Security (PIPE-006)

- Ensure all workflow files set explicit top-level `permissions: contents: read`.
- Restrict job-level `id-token: write` and `pull-requests: write` exclusively to steps requiring GCP Workload Identity Federation or GitHub API comment/review creation.

## 4. Code Comments & Potential Conflicts Analysis

A comprehensive audit of the codebase (`.github/workflows/*`, `.github/dependabot.yml`, `Makefile`, and `k8s-operator/`) was conducted to evaluate potential conflicts and align the design with inline codebase comments. The following explicit questions are raised for alignment and review:

1. **Event Triggers & Zizmor Ignore Annotation (`.github/workflows/auto_request_review.yml:4`):**  
   In `.github/workflows/auto_request_review.yml`, there is an inline comment: `# zizmor: ignore[dangerous-triggers] - requesting a reviewer needs pull-requests: write, which pull_request cannot grant on fork PRs; no checkout, no other secrets`. Our proposed design preserves `pull_request_target` with `pull-requests: write` because it is required for fork PR reviewer assignment without checking out untrusted code.
   - _Question 1:_ Does the inline `# zizmor: ignore[dangerous-triggers]` comment in `.github/workflows/auto_request_review.yml` satisfy our security governance requirements for `pull_request_target` triggers, or should this workflow be refactored into a two-workflow (`pull_request` + `workflow_run`) pattern to avoid `pull_request_target` entirely?

2. **Gosec Security Scanner & `#nosec` Directives (`k8s-operator/`):**  
   In `k8s-operator/internal/controller/platformagent_manifests.go:75` (`// #nosec G101 -- Policy JSON schema definition, not credentials`) and `k8s-operator/internal/testing/testutil/testutil.go` (`// #nosec G301`, `G304`, `G306`), existing code comments instruct Go security scanners (`gosec`) to ignore specific false-positive security rules, and file permissions for test fixtures are tightened (`0750` for directories, `0600` for files). Because these annotations and tightened file modes resolve all false-positive findings cleanly, the `gosec-scan` job in `.github/workflows/security-scan.yml` runs in blocking mode (`args: "./k8s-operator/..."` without `-no-fail`), ensuring that any new unsafe Go patterns block pull requests as intended by PIPE-003.
   - _Question 2:_ Will the proposed `.github/workflows/security-scan.yml` `gosec` scan job (running with `args: "./k8s-operator/..."`) properly honor these inline `#nosec` directives without failing CI, or should we pass explicit exclusion flags or rules to `gosec` in the workflow YAML?

3. **Container Image Pinning vs. Runner Manifest Resolution (`security-scan.yml`):**  
   Reviewer feedback on PR #388 requested pinning the `semgrep/semgrep` container image to an explicit version and SHA256 digest (`semgrep/semgrep:1.82.0@sha256:4a38618e7c10c14b98d1a10065aefc8c1050beab45eead11b33da07d7ccbeec1`). However, during CI testing, pinning container images to static SHA256 digests caused manifest resolution failures in GitHub Actions runner containers, requiring a switch to `semgrep/semgrep:latest`.
   - _Question 3:_ Given that pinning container images to SHA256 manifest digests caused resolution failures in GitHub Actions runner containers, should we permit `semgrep/semgrep:latest` in `security-scan.yml`, or should we require an explicit release tag (without digest) for container images in workflow jobs?

4. **Checkov Soft Fail vs. Hard Fail Configuration (`soft_fail`):**  
   In `.github/workflows/security-scan.yml`, Checkov is configured to scan all Infrastructure-as-Code (IaC) files across the repo. A hard-fail setting (`soft_fail: false`) causes Checkov to fail CI on pre-existing repository manifests and workflows.
   - _Question 4:_ Should Checkov be configured with `soft_fail: true` so that pre-existing IaC findings are reported in build logs without blocking pull requests, or should we define a `.checkov.yaml` baseline file to enforce hard failures on new findings only?

5. **Dependabot Docker Directories (`/agents/operator` and `/agents/devteam`):**  
   Earlier design notes mentioned monitoring `/agents/operator` and `/agents/devteam` in `.github/dependabot.yml`, but those directories do not currently exist in the repository (only `/deploy/docker` and `/agents/platform` exist).
   - _Question 5:_ Should `.github/dependabot.yml` be scoped strictly to existing Docker directories (`/deploy/docker` and `/agents/platform`), or should entries for `/agents/operator` and `/agents/devteam` be added preemptively for planned agent personas?

6. **Static Scanner Ignores (`.trivyignore.yaml` and Zizmor Annotations):**  
   During CI validation, Trivy flagged rule KSV-0118 on Kustomize overlay patch files in `k8s-operator/config/integrations/` where `securityContext` is intentionally omitted because it is merged into target deployments, KSV-0046 on sample read-only explorer ClusterRoles (`platform-agent-explorer`) using wildcard resource read permissions, KSV-0112 on sample read-only explorer Roles (`developer-team-agent-explorer`) using wildcard resource read permissions, and GCP-0061 / GCP-0048 on staging PoC Terraform configurations (`k8s-operator/testing/staging_workloads/main.tf`). Similarly, Zizmor flagged Medium-severity `secrets-inherit` rules on reusable integration workflows (`staging-redeploy-integrations.yml`, `autopush-redeploy-integrations.yml`) and `dependabot-cooldown` warnings on `.github/dependabot.yml`. To prevent plain-text ignore rules from suppressing checks repository-wide on production targets, these rules are explicitly scoped using the YAML ignore format (`.trivyignore.yaml`), which applies `paths` selectors per rule (`KSV-0118`, `KSV-0046`, `KSV-0112`, `GCP-0061`, `GCP-0048`, `DS-0002`, `KSV-0014`, and `KSV-0050`). Additionally, Trivy rule DS-0029 flagged missing `--no-install-recommends` flags on `apt-get install` commands in `deploy/docker/Dockerfile`, which were resolved by adding `--no-install-recommends`, and rule DS-0002 was addressed on `deploy/docker/Dockerfile` by explicitly dropping to non-root `USER 10000:10000` at the end of both published stages (`platform` and `credential-proxy`).
   - _Question 6:_ Does scoping KSV-0118, KSV-0046, KSV-0112, GCP-0061, GCP-0048, DS-0002, KSV-0014, and KSV-0050 in `.trivyignore.yaml` with explicit path selectors and addressing DS-0002 directly via non-root `USER 10000:10000` in `deploy/docker/Dockerfile` align with repository governance rules for Kustomize overlay patches, sample Roles/ClusterRoles, staging test-workload manifests, and production container images?
